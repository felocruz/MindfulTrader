# Spec: Predator Fusion — Transformer Signal Staleness Decay

**Status**: Design proposed, queued for pickup — not started. User has confirmed the design
direction (continuous decay via `PredictionAgeUs()`, not a hard freshness gate) but the decay
function's specific form/time-constant is an open question requiring empirical derivation
before implementation, not a value to invent now.

**Retargeted, 2026-08-24, same day (file name kept as-is to avoid breaking existing
cross-references, but the actual consumer changed)**: Predator Fusion is confirmed
training-time-only — it never runs live, so it never consumes this decayed signal.
`PredictionAgeUs()` and the decay mechanism itself are still needed and still designed exactly as
below; the consumer is now **the meta-labeler's own live inference**, not `TurtleSoupFusion.h`'s
entry-fusion functions. Section 2 item 3 below is superseded by this — see the note inline. See
`MindfulTrader/docs/superpowers/specs/2026-08-24-two-classifier-cpp-deployment-spec.md` Section 3
item 3, and `PRODUCTION_TRIAGE.md` §0/row 11.

## 1. Motivating context — a real, verified gap, not a hypothetical one

Found while reviewing the production pipeline cross-project (`lbrnet`'s
`PRODUCTION_TRIAGE.md`, 2026-08-24 session). The user's own mental model: "Predator Fusion
should work with the last signal generated by the Transformer, making sure it decays since
the C++ works on every tick but the Python side makes a prediction only when indicator deltas
or 16D observation change." Verified directly against the actual code (not assumed) that this
integration does not exist yet:

**What already exists, verified by reading the code directly:**
- `FreshnessGateEngine::IsFresh(nowUs, lastWriteUs, maxAgeUs, bypassCheck)`
  (`include/FreshnessGateEngine.h:31`) — a generic, reusable binary freshness primitive.
- `InferenceManager::HmmStateAgeUs(nowUs)` / `IsHmmStateStale(nowUs, maxAgeUs=5'000'000ULL)`
  (`include/InferenceManager.h:69,73`) — proper continuous age tracking + a binary staleness
  check for the HMM regime state, safe-closed (stale if never updated).
- `InferenceManager::IsPredictionFresh(nowUs, maxAgeUs)` (`include/InferenceManager.h:120`,
  impl `src/InferenceManager.cpp:178-180`) — the same binary pattern, but for the Transformer's
  `PredictionState`. **Confirms the underlying freshness plumbing for the prediction already
  exists.**

**What does NOT exist, verified by reading the code directly:**
1. **No continuous age getter for the prediction.** `HmmStateAgeUs()` returns actual elapsed
   microseconds; there is no `PredictionAgeUs()` equivalent — only the boolean
   `IsPredictionFresh()`. Real decay needs a continuous age value; that raw ingredient isn't
   exposed yet.
2. **`TurtleSoupFusion.h`'s live entry-fusion functions (`EvaluateTurtleSoupOptionA`,
   `EvaluateTurtleSoupOptionB`) take no Transformer-signal input of any kind** — not the raw
   prediction, not `modelConfidence`, not freshness. They are self-contained price-action
   pattern detectors (bar geometry vs. a 20-bar reference range + ATR). There is currently
   nothing in the live entry-fusion path for a decay weight to even apply to.

**Conclusion**: this is not a bug in something that was supposed to already be wired — Predator
Fusion Option A was built and shipped first as a self-contained, independently-testable
price-geometry detector, which was a reasonable place to start. The Transformer-signal fusion
(with staleness handling) is genuinely new, scoped work, not a regression.

## 2. Design (confirmed direction: continuous decay, not a hard gate)

User's explicit preference: **`PredictionAgeUs()`** — a continuous age value feeding a decay
function, not a binary fresh/stale cutoff (the pattern already used for `IsHmmStateStale`).
Rationale (from this session's discussion): the Python side updates on indicator-delta/16D
observation change, not a fixed cadence, so the true inter-update interval varies — a hard
cutoff either discards a still-useful signal too early or trusts an overly-stale one right up
until an arbitrary line. A continuous decay degrades the signal's influence smoothly as it ages,
without needing a single "correct" cutoff.

**Three concrete pieces of work:**

1. **Add `InferenceManager::PredictionAgeUs(uint64_t nowUs) const`** — mirrors
   `HmmStateAgeUs()` exactly (`include/InferenceManager.h:69`), same file, same class,
   same pattern. Mechanical, low-risk.
2. **Design and implement a decay function applied to `modelConfidence`** as a function of the
   new age value, before that confidence is used by any fusion function. Candidate forms
   (not yet chosen — see Section 3): exponential (`w(age) = exp(-age / tau)`), linear ramp to
   zero at some cutoff, or a piecewise step matching the existing binary convention as a
   fallback. **`tau` (or the equivalent parameter for whichever form is chosen) is the load-
   bearing open question — see Section 3, do not pick a round number.**
3. **Superseded, 2026-08-24: wire the (now-decayed) Transformer signal into the meta-labeler's
   live inference, not into `EvaluateTurtleSoupOptionA`/`OptionB`.** Predator Fusion is
   training-time-only (see the retargeting note at the top of this spec) — there is no live
   entry-fusion function left to wire this into. The decayed signal becomes one of the
   meta-labeler's own live input features (`MindfulTrader/docs/superpowers/specs/
   2026-08-24-two-classifier-cpp-deployment-spec.md` Section 3 item 3), combined there with the
   soft classifier's score, HMM scalars, and sizing multipliers by whatever the meta-labeler
   learns during training — not a hand-designed gate/scale/AND-OR combination rule, since that
   composition is now the meta-labeler's own job, not hand-crafted fusion logic.

## 3. Open questions — explicitly deferred, not to be filled with invented numbers

1. **Decay function form and time constant.** General principle is real and citable —
   Grinold & Kahn's Information-Coefficient/signal-decay framework (*Active Portfolio
   Management*) establishes that predictive signal value degrades over time and that decay
   should be modeled explicitly, not ignored — but that literature's own empirical half-lives
   (months, for cross-sectional equity factors) are the wrong scale entirely for this problem
   (seconds-to-minutes, single-instrument, intra-day). **The correct time constant must be
   derived from this system's own data, not borrowed from that literature and not invented.**
   Concrete first step when this is picked up: pull the actual inter-prediction-arrival interval
   distribution from historical logs (how often does an indicator-delta/16D-observation change
   actually trigger a new Python-side prediction, under real market conditions) — that
   distribution is the empirical basis for choosing a decay form/constant, the same discipline
   already applied this week to the HMM's block-length/window-size derivation
   (`lbrnet`'s `docs/superpowers/specs/2026-08-24-hmm-gate-threshold-calibration-institutional-
   grade-spec.md`, Section 5(b)/(d) — same principle, different system).
2. **Superseded, 2026-08-24**: "how the decayed signal combines with a fusion function's own
   price-geometry score" no longer applies — there's no live fusion function to combine with
   (Predator Fusion is training-time-only). The combination question moves entirely to the
   meta-labeler's own training, which learns how to weight this feature alongside the others —
   not a hand-designed gate/scale/AND-OR rule.
3. **Superseded, 2026-08-24**: same reason — Option A, Option B, and any future named-pattern
   fusion functions never consume this live, so "does it apply uniformly across them" is moot.

## 4. Non-goals

- Not touching the existing HMM staleness handling (`HmmStateAgeUs`/`IsHmmStateStale`) — it
  already works and is out of scope.
- Not implementing the hard-freshness-gate alternative — the user has already decided on
  continuous decay.
- Not deciding the decay parameter now — Section 3 Item 1 is deferred to when this work is
  actually picked up, with its own empirical-derivation step, not filled in speculatively here.

## 5. Validation plan (once implemented)

- Golden-vector regression test for `PredictionAgeUs()` itself — mechanical, mirrors the
  existing test pattern for `HmmStateAgeUs()`.
- Per this project's own existing convention for exactly this class of function
  (`TurtleSoupFusion.h`'s own comment on `EvaluateTurtleSoupOptionB`: "this function's output
  must be verified against the Python model's own predict_proba() for a comprehensive set of
  real inputs") — the decay function's output must be verified against a Python-side reference
  implementation of the same decay math for a comprehensive set of real (age, confidence) pairs,
  not just synthetic inputs chosen to make the C++ math compile.
- A test confirming the decay function's behavior at the boundaries: age=0 (no decay), age→∞
  (fully decayed / matches whatever the "no signal" default behavior should be), and a
  monotonicity check (older signal never has more influence than a fresher one, all else equal).
