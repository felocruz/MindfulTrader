## How to use this doc

Each pillar has a status table. **Status** values:
- `validated` — matches a named, cited literature convention or an internally consistent, well-reasoned finance-specific adaptation.
- `plausible-engineering-choice` — not derived from a specific paper, but a reasonable, low-stakes rolling-feature choice (this is an ML input, not a hypothesis test — see the recurring distinction below).
- `under-powered` — literature suggests the current sample size/window is below what's needed for the estimator to be reliable.
- `needs-empirical-validation` — plausible on paper, but should be checked against this project's own ES/MES data (Weron-style Monte Carlo, bootstrap MSE, etc.) before trusting further.
- `pending-replacement` — the literature critique isn't a tuning question at all; the leading hypothesis is that the current statistic itself should be swapped for a named robust alternative, not merely re-parameterized. Stronger than `under-powered`. Empirical validation still gates the actual swap, but the expectation going in is replacement, not vindication.

**A recurring distinction that applies throughout:** most of these calculators feed an HMM as *rolling ML features*, not formal hypothesis tests. A window that would be too short for, say, Lo & MacKinlay's variance-ratio test can still be a perfectly reasonable rolling feature — noise in one of sixteen inputs is not the same failure mode as an invalid test statistic. Ratings below call this out explicitly where it changes the verdict.

## Cross-Pillar: FeatureScaler Ingestion (Shannon-motivated, all pillars affected)

**Not one of the four calculator pillars above — this is the shared scaling layer all 16 dims pass through**
(`FeatureScaler.h`), added to this doc 2026-08-13 per its own in-scope listing (line 8) never having
been evaluated against the Gang literature directly.

**Context:** `FeatureScaler`'s core estimator — median location + `1.4826×MAD` scale (`FeatureScaler.h:205`,
already commented "Taleb-consistent") — is the textbook-correct choice for fat-tailed data and is not in
question. The defect under investigation (`docs/superpowers/specs/2026-08-12-featurescaler-sentinel-collapse-hardening.md`,
`FeatureScaler` D2 diagnostic firing live in production, ~61-71% exact-zero rate measured in exported
`.context` training data for dims 1/2) is upstream of the estimator: raw calculators' carry-forward fix
(D1, this doc's Pillar-specific rows above) correctly stops fabricating a sentinel, but a carried-forward
value still repeats in the rolling window many times in a row, and a correctly-functioning robust
estimator legitimately converges its median onto a value that dominates its input — the estimator isn't
misbehaving, the input stream is contaminated with zero-marginal-information repeats
(`H(X_t | X_{t-1}) = 0` for an exact repeat, per Shannon).

**Working design direction (not yet approved/implemented):** de-duplicate consecutive-identical raw
values before they enter the rolling window, so the window represents a bounded number of *informative*
observations rather than N raw ticks.

**2026-08-13 literature-grounding pass — results, reported honestly:**

1. **Market microstructure (closest analogous problem, but targets a different estimand).** Zhang, Mykland
   & Aït-Sahalia (2005, "A Tale of Two Time Scales," JASA 100) and the realized-kernel program
   (Barndorff-Nielsen, Hansen, Lunde & Shephard 2008, Econometrica; Hansen & Lunde 2006, J. Business &
   Economic Statistics) both treat stale/zero-return ticks as noise contaminating a *variance-of-returns*
   estimator, and their fix is statistical correction (subsample-averaging, autocovariance-kernel
   downweighting), not deletion. Separately, the *data-cleaning* literature (Brownlees & Gallo 2006,
   "Financial Econometric Analysis at Ultra-High Frequency," J. Financial Econometrics) does explicitly
   deduplicate stale prints — but as raw-tick hygiene, not as a correction to the estimator itself. Neither
   maps exactly onto a rolling median/MAD *of levels*, which is a different estimand than realized variance.
2. **Robust statistics literature — silent on this specific failure mode.** Rousseeuw & Croux (1993, JASA)
   and follow-on finite-sample work (Akinshin 2022, arXiv:2209.12268) discuss MAD's breakdown point and
   efficiency exclusively under *outlier* contamination (a minority of points displaced far from center).
   Repeated-value/tie contamination is a structurally different failure mode (majority-convergence, not
   breakdown) and does not appear to be treated as a named separate case anywhere in the classical robust-
   statistics canon (Huber; Rousseeuw & Croux). **This is the weakest-grounded of the findings below — an
   absence, not a citation.**
3. **HMM/regime-switching literature — the closest real precedent, at a different layer.** Zucchini,
   MacDonald & Langrock (*Hidden Markov Models for Time Series*, 2nd ed., CRC Press, missing-data chapter)
   give the standard HMM treatment of a non-fresh/unavailable observation: mark it missing and skip the
   emission-density update for that time step entirely, letting the state distribution propagate through
   the transition matrix alone. Same underlying instinct as the proposed fix (a stale reading shouldn't
   behave as a fresh independent draw), but implemented at the *likelihood* level, not the *feature-scaling*
   level — this codebase's HMM consumes already-scaled features, so this precedent doesn't transfer
   mechanically, only in spirit. Bulla & Bulla (2006, Computational Statistics & Data Analysis, Student-t
   HMMs) addresses fat-tailed emissions but not held-value/imputation preprocessing.
4. **Is dedupe-at-ingestion itself a named technique? No, but a closely-related principle is — precisely
   scoped, 2026-08-13 addendum.** Not itself named in market microstructure, robust statistics,
   HMM/state-space, or general streaming-ML feature engineering literature. "Plateau"/"flat spot"
   terminology exists but in unrelated signal-processing contexts (e.g. cosmic-ray rejection in imaging).
   External review (Gemini, via `../lbrnet/logs/rc_gemini.log` `GEMINI_BRIEF_089_RESPONSE`) correctly
   points out that skipping duplicate-value pushes turns the rolling window from a clock-time window
   (last N ticks) into an **event-time / information-time window** (last N *distinct* observations) —
   and event-time sampling (tick bars, volume bars, information-driven bars) is itself a well-established
   market-microstructure convention (Mandelbrot & Taylor's early trade-time sampling; formalized in
   Easley, López de Prado & O'Hara's information-driven-bars work) for exactly the reason given here:
   removing zero-information/stale observations from corrupting a statistic computed over the window.
   **Scoped precisely, not overclaimed**: that literature is about *raw price-bar construction* (deciding
   when a new *bar* forms), not *feature-scaler rolling-window ingestion* (deciding when a new *sample*
   enters an already-formed dim's window) — this fix applies the same underlying principle one layer
   downstream of where the cited literature classically applies it, not a direct implementation of it.

**Honest verdict:** the proposed fix is **partially grounded — a principled synthesis, not a direct
implementation of an established named method.** The direction (a stale/repeated reading shouldn't count
as a fresh independent draw) is strongly consistent with three independent bodies of consensus practice
(microstructure's stale-tick-exclusion convention; HMM's missing-data-marginalization convention; and, per
the 2026-08-13 addendum above, event-time/information-time sampling's rationale for excluding
non-informative observations from a windowed statistic), and the Shannon zero-marginal-information framing
is sound information theory, correctly applied. But no source directly prescribes deduplication as a
preprocessing step for a rolling median/MAD estimator specifically, classical robust statistics doesn't
treat tie-contamination as a distinct problem from outlier-contamination at all, and the closest named
convention (event-time bars) classically operates one layer upstream (bar formation, not post-formation
feature-window ingestion). Document and defend this internally as a synthesis that sits adjacent to real
named conventions, not as "the literature says to do this."

**Status: `plausible-engineering-choice`** (low-risk given it changes only which observations enter an
already-correct estimator, not the estimator itself — but should be presented to stakeholders with the
grounding-level honesty above, not overclaimed).

## Findings, not literature questions

These are naming/labeling/dead-code issues the inventory surfaced. They don't have a "right value" — they have a right fix, tracked here so they aren't lost, but implementation is separate from this spec's parameter-tuning scope.

1. **`fisher_info` (dim 8) is not statistical Fisher information.** It's Ehlers' technical-analysis *Fisher Transform* — confirmed to borrow R.A. Fisher's 1915/1921 variance-stabilizing z-transformation (`0.5·ln((1+x)/(1-x))`, originally for correlation coefficients) but repointed at normalized price position, with a window (30-120 bars) 3-12× longer than Ehlers' own documented 9-10 bar convention. Recommend renaming/re-documenting to stop implying real Fisher information in the schema and docstrings.
2. **TS3's Hurst subgraph is UI-labeled "R/S"** (`TripleScreen3.cpp:338`) but the actual computation is DFA (`CalculateHurstExponent`). Stale label from before the "ELITE v2.6" R/S→DFA migration mentioned in `StudyHelperFunctions.cpp:2458-2474`.
3. **`StructureEngine::GetFractalDimension()`'s comment claims Sevcik's method; the formula is a raw path-length/displacement ratio**, not Sevcik's log-log calculation. Either fix the formula to match Sevcik, or fix the comment to stop citing him.

6. **Correction, 2026-08-13 (Task 11 of the institutional-elevation plan):** the three functions below are **not** dead code — this finding's original "no call sites found anywhere in the searched codebase" claim was wrong; the original sweep didn't search `tests/cpp/`. `StructureEngine::GetRecurrenceRate()` (4 call sites), `InformationEngine::GetFisherInformation()` (1 call site), and `InformationEngine::GetRecurrenceRate()` (5 call sites) all have real, passing unit tests in `tests/cpp/test_structure_engine.cpp`/`test_information_engine.cpp` exercising cold-start, warmup-gate, reset, and regime-sensitivity behavior.
